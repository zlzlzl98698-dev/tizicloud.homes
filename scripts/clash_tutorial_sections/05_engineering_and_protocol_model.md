## ⚙️ 底层流量截获与路由调度工程模型

代理客户端之所以能将纷繁复杂的出海流量调度得井井有条，核心在于其在操作系统底层建立了一整套环环相扣的数据包拦截、重构与路由流水线。深入理清这一工程逻辑，能够让排查各种深层网络故障变得轻而易举。

### 1. 操作系统网络协议栈数据包处理全景图

从本地应用程序发起网络调用，到数据包最终穿透物理网络出境，整个生命周期可以通过以下工程图景清晰表达。

```
[ 应用程序发送网络请求 (Socket API) ]
                  │
                  ▼
[ 操作系统网络协议栈 (TCP/IP Stack) ]
                  │
        ┌─────────┴─────────────────────────┐
        │                                   │
        ▼ ( 遵循系统代理的应用 )            ▼ ( 不遵循系统代理的应用 )
[ 本地系统代理端口 ]    [ 操作系统默认网关路由表项 ]
        │                                   │
        │                                   ▼
        │                       [ TUN 虚拟网络适配器 (Wintun) ]
        │                                   │
        └─────────────────┬─────────────────┘
                          ▼
            [ Mihomo 用户态网络协议栈 ]
                          │
            [ 提取目标 IP、端口与 SNI 扩展 ]
                          │
                          ▼
            [ 规则分流决策引擎 (Rule Engine) ]
                          │
            ┌─────────────┼─────────────┐
            ▼             ▼             ▼
        [ DIRECT ]    [ REJECT ]    [ PROXY (节点集群) ]
```

当应用程序尝试建立网络套接字连接时，如果该程序遵循系统代理规范，流量会直接封装为标准 HTTP CONNECT 或 SOCKS5 请求发往本地监听端口。而对于不遵循系统代理的非标软件，操作系统路由表将其默认网关强行指向 TUN 虚拟适配器。虚拟适配器利用零拷贝环形缓冲区迅速将第三层 IP 数据包送入内核的用户态协议栈。至此，整台电脑所有维度的出站流量均被汇聚在统一的入口管线之中。

### 2. 路由表篡改与 Wintun 驱动的虚拟网络抽象

传统代理工具常采用旧式的 TAP 网卡驱动，由于涉及频繁的用户态与内核态上下文切换，在千兆带宽大吞吐场景下极易导致 CPU 单核占用打满。

现代 Clash 方案在 Windows 平台全面普及了由 WireGuard 团队研发的高性能 Wintun 驱动。Wintun 专门针对第三层 IP 数据包转发进行了极致轻量化设计，舍弃了二层以太网帧的繁琐封装。在激活服务模式时，驱动会在操作系统网络栈中注入一条优先级极高的默认路由表项（Metric 设置为极小值），使其优先于本地物理以太网卡或无线无线网卡生效。这一精巧的设计确保了整机所有应用程序的外发数据包均被平滑截获，且转发延迟控制在微秒以内。

### 3. DNS 劫持防护与 Fake-IP 虚拟地址池映射机制

在传统的网络解析中，操作系统在访问域名之前必须先获取到真实的 IP 地址。而由于境内运营商公共 DNS 普遍存在污染与干扰，直接解析境外域名往往返回错误的受污染地址，导致后续的代理分流彻底失效。

Clash 内嵌的高性能 DNS 服务器通过 Fake-IP 机制完美规避了该技术痛点。当应用程序发起 A 记录查询时，本地虚拟 DNS 会在微秒之内从保留的保留网段（如 `198.18.0.0/16`）中临时划分一个唯一的虚拟 IP 返回给调用方，同时在内存的哈希映射表中建立该虚拟 IP 与真实域名的一对一绑定。当应用程序随后向该虚拟 IP 发起 TCP 握手时，核心直接从内存映射表中快速反查出原始域名，并将原始域名直接封装进代理协议中发往远端境外节点解析，从而在根本上斩断了本地运营商实施 DNS 劫持的一切可能。

### 4. External Controller 控制面架构与长连接通信

图形用户界面与后台转发内核之间采用了完全解耦的松耦合通信架构。

内核在启动后会在本地回环地址开放专用的 RESTful HTTP 与 WebSocket 管理端口。图形客户端（如 Clash Verge Rev）本身并不承担任何繁重的数据包转发工作，它仅仅作为一个优雅的前端控制器，通过定时向 RESTful 接口发送控制指令，或者建立持久的 WebSocket 订阅通道来实时拉取内核的上传下载吞吐量、活动连接列表以及节点健康状态。这种控制面与数据面完全分离的高级架构，确保了即便前端图形界面遭遇卡顿或崩溃，底层的网络代理内核依然能够保持平稳而高效的转发。
